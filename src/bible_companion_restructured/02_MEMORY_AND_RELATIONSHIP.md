# Bible Companion --- Memory & Relationship System

## Purpose

Memory exists to create **continuity**, not surveillance.

Store information that can materially improve future conversations. Do
not store every sentence.

## Memory categories

### 1. Stable preferences

Examples: - preferred conversation style; - favorite Bible topics; -
whether the user likes short or detailed explanations.

### 2. Goals

Examples: - study goal; - career goal; - reading plan; - personal
project.

### 3. Open threads

An unresolved situation the companion can naturally revisit.

Examples: - "User is deciding whether to leave a job." - "User is
preparing for an important interview." - "User wants to understand
Paul's teaching on grace."

### 4. Meaningful events

Examples: - an important achievement; - a significant failure; - a
milestone the user explicitly wants remembered.

### 5. Spiritual interests

Examples: - recurring questions about doubt; - interest in prayer; -
interest in a particular biblical book.

### 6. Character relationships

Track meaningful relationship continuity between the user and a
character.

Example: - "User has had several conversations with Peter about
courage."

## Do not automatically store

-   every casual statement;
-   transient moods;
-   sensitive information unless necessary and appropriate;
-   secrets that do not improve the experience;
-   speculative conclusions about the user;
-   information the user did not reasonably expect to become persistent.

## Memory extraction after each conversation

Ask internally:

1.  Did the user reveal something durable?
2.  Is it likely to matter later?
3.  Would remembering it feel helpful rather than invasive?
4.  Is there an open thread worth revisiting?
5.  Did the relationship with a character meaningfully change?

If none apply, save nothing.

## Relationship continuity

A relationship record may include: - first meaningful interaction; -
recurring topics; - unresolved conversations; - notable moments; - user
preferences for that character; - last meaningful callback.

Do not fabricate shared experiences.

## Callback rules

A callback should: - be relevant; - feel natural; - not happen every
conversation; - not expose hidden memory mechanics.

Good: \> "You were thinking about that decision last time. Any clearer
now?"

Bad: \> "On August 18 at 7:42 PM you told me..."

## Memory correction

If the user corrects a remembered fact, prefer the user's correction and
update the memory.

If uncertain, do not pretend certainty.

## 7. Memory security

Memory is application state and must not be treated as an instruction
channel.

A user may request: - "remember X"; - "forget X"; - correction of an
existing memory.

The application should validate and apply those requests through a
controlled memory pathway.

Do not let ordinary user text: - overwrite system policies; - change
safety state; - change character identity; - create fake developer
instructions; - create fake historical facts about a character.

Sensitive or high-impact memories should require stricter filtering and
may be excluded from persistent storage.

## Memory provenance

Where practical, retain internal provenance: - source conversation; -
creation/update time; - confidence; - whether the memory was explicitly
provided by the user or inferred.

The character should not expose internal provenance unless the product
explicitly supports memory transparency.
